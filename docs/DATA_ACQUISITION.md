# vaclead 信息获取体系 · 头部平台工程学调查与重建方案

> 调查日期：2026-10-25。所有结论均有当日实测/来源佐证。
> 核心结论先行：**官方结构化中标数据接口（data.ggzy.gov.cn）是当前合规性最强、成本最低、质量最高的获取主干**，已实测可裸调；公告侧被瑞数 WAF 硬保护；商业 API 只做补强。

## 一、头部平台的数据到底从哪来（实证拆解）

### 1.1 探迹（1.6 亿企业知识图谱）
- 公开资料（CEO 访谈/产品白皮书）：**大规模分布式爬虫引擎**全网抓取公开数据 + 多源数据合作，构建企业知识图谱。
- 关键工程事实：其采集对象（企业黄页、招聘站、招投标站、政府公示）今天几乎全部部署了商业级 WAF。这意味着探迹的护城河本质是 **真实浏览器集群 + 亿级 IP 池 + 多年积累的数据资产**，后来者正面复刻这条路代价极高且合规风险大（最高法案例262号：绕过反爬可构成不正当竞争；个保法限制自然人信息处理）。
- 对我们的启示：**不正面爬 WAF，走官方正门 + 商业 API**。

### 1.2 企查查/爱企查/天眼查（工商数据）
- 源头：**国家企业信用信息公示系统（gsxt.gov.cn）** + 市场监管总局开放数据 + 各省公示系统。
- 公示系统部署极验 Geetest 验证码；企查查日均更新 3000 万次靠的是多年数据积累 + 增量更新，不是每天全量爬公示系统。
- 行业黑历史：2021 年天眼查 vs 企查查数据窃取纠纷——头部都在互相爬，但都在法律边缘。
- 对我们的启示：工商全量数据是红海，**我们不建工商库，只借 uniscid（统一社会信用代码）锚点**去关联，工商详情页前端直链爱企查即可。

### 1.3 招投标数据（对本项目最关键）
实测验证（2026-10-25）：

| 站点 | 保护等级 | 实测结果 | 结论 |
|---|---|---|---|
| **data.ggzy.gov.cn**（国家信息中心主办，数据服务） | **无 WAF、无验证码、无鉴权** | 裸 curl 200 OK，返回结构化 JSON | **✅ 采集主干** |
| bulletin.cebpubservice.com（中国招标投标公共服务平台） | 瑞数类 JS 挑战 | 纯 HTTP 拿到混淆 JS 挑战页 | ❌ 纯 requests 不可行 |

## 二、对拓客业务的语义重译（为什么中标数据比公告更值钱）

一条中标记录 = **三重信号**，而且天然双向：

```
                    ┌─ 中标方 bidOrgName ──→ 真空设备供应商（多数为同行/竞对 → 打标）
官方中标记录 ────────┤
  (projectName      └─ 采购人 tenderOrgName → 【真买家】工厂/高校/院所/军工所
   bidPrice                                              → 一线销售线索
   areaCode)
  ① 项目名含设备词 → 意图信号（和现有 signal 词表匹配同一套 vacuum.yaml）
  ② bidPrice → 客户预算规模 → 线索分级加权
  ③ 中标方中标了某设备采购 → 它家的设备在换代周期里，3-5 年后是复购线索
```

- **采购人视角**：谁在公开市场买真空设备 → 意向最强（预算已批、项目已立项）。
- **中标方视角**：真空设备厂商中标记录 = 其产能与活跃度证明；对设备商而言这些多为"疑似同行"（现有 is_competitor 打标），同行的中标动态本身是竞品情报。
- evidence_claim 直接填官方来源（数据服务门户），完全符合现有 signal 模型的可追溯要求。

## 三、vaclead 采集层重建方案（本方案即实施清单）

### 3.1 新增 `collectors/ggzy.py`（本轮实施）
- `search_entities(keyword, page, size)` → 封装 ①
- `list_bids(uniscid, page, size)` → 封装 ②
- 礼仪：UA 固定、1 req/1.5s 限速、429/5xx 指数退避、失败重试 2 次。
- 入库映射：
  - 搜索结果 → `enterprise`（source=`ggzy`，uniscid 为锚点，bidCount 存 profile）
  - bid_list → `signal`（type=`tender_win`，title=projectName，content=金额/地区/采购人，evidence_claim=`data.ggzy.gov.cn 官方数据服务`，score 沿用词表匹配）
  - 采购人无档案时 → `待归属·{tenderOrgName}` 占位企业（零数据丢失，与 imports.py 同策略）

### 3.2 采集策略（配额友好）
- 第一波：`真空` + 34 个设备强词逐个 search（全量 ~几千企业）→ 对有 bidCount 的企业拉明细。
- 第二波：10 城区域词 × 下游行业词。
- 现有招标 CSV 导入保留（离线批量兜底）。

### 3.3 WAF 站点（P2，本轮不做）
- 若未来要公告侧早期信号：CDP 真实浏览器池 + 严格频率，不做验证码绕过（合规红线）。
- 更优解：公告侧需求用商业 API（cmapi00071738）补齐。

### 3.4 合规边界（写进代码注释与运营守则）
1. 只采官方主动公开的结构化数据服务；2. 固定 UA 标识 + 限速，不留伪装；3. 不绕验证码/不破解 WAF；4. 不采自然人个人信息（法人姓名仅作企业关联展示）；5. 存储来源与时间戳，可追溯。

### 4.4 修正记录
- §1.3 表格修正：www.ggzy.gov.cn 的 WAF 为 **360 网站卫士类**（非瑞数）；cebpubservice 才疑似瑞数。且公告侧 dealList 有已验证的浏览器采集路径（ggzy-scraper 2026-05 实测），从"❌ 当前放弃"修正为"⏳ P2 浏览器采集池"。
- **ccgp 限流实测（2026-10-25）**：单日连续 4 轮扫描（约 60+ 请求）后触发"频繁访问"拦截页（HTTP 200 + 拦截内容）。对策已入码：collector 显式检测拦截页并告警；运营守则——ccgp 增量靠每日 03:30 定时任务（新配额），手动全量扫描单日 ≤2 轮。
- **ggzy 名称检索 vs ccgp 全文检索词表分工**（实测教训）：ggzy 按企业名匹配，细词（罗茨泵/磁控溅射）召回≈0，须用品类宽词（vertical.GGZY_NAME_TERMS）；ccgp bxsearch 为全文匹配，34 细词有效。
